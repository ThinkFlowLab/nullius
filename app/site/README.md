# The Nullius website

The searchable documentation, built with MkDocs and Material, in the Nullius
identity: the supplied circle-and-slash mark and outlined Instrument Serif wordmark, DM Sans for reading and interface headings, and IBM Plex Mono for code. The
project's front page lives on the domain above the documentation, outside this
repository.
The documentation sidebar groups pages into Get started, Run evaluations,
Understand results, Benchmarks, Agents, Capabilities, CLI and Settings, in that
order: a reader's path from a first run to the reference. Each catalogue
category has Supported, Add manually and Add with an assistant pages. Run
evaluations has the builder; CLI has a page per topic of the command line;
Settings has separate provider, key and host pages. Reference holds the
standard, the worked example, the architecture and the metric definitions.
The documentation's dark palette uses a near-black background (`#060606`) and
dark panels (`#141414`), separate from the application's grey surfaces.
It defaults to dark; the theme toggle preserves the reader's
selected appearance. The previous/next footer follows the article's width,
leaving both navigation columns outside it.

The site has no runtime dependency on Flask, Node, a database, or the application.

## Build and preview

From the repository root:

```bash
uv run --no-project --with-requirements app/site/requirements.txt python app/site/build.py \
  --site-url http://localhost:8793/
python3 app/site/check.py app/site/dist --site-url http://localhost:8793/
python3 -m http.server 8793 --bind 127.0.0.1 --directory app/site/dist
```

Open <http://localhost:8793>. Rebuild after editing a source file, then refresh.
Sidebar links use Material's instant navigation: content, navigation state and
the table of contents update without reloading the document. Desktop sidebar
clicks preserve the navigation rail's scroll position. The preview
`--site-url` must use the path where it is served, because instant navigation
uses the generated sitemap. The build also works from another working directory when given the absolute
path to the build script. Generated output is ignored by Git.

## Source ownership

- `docs/` in the repository is the website: its README is the front page and
  each folder a section. Edit those Markdown files directly; their edit links
  point back to the originals. A
  navigation entry naming a folder's README.md lists that folder's generated
  pages under it (`hooks.py`), so a new benchmark, agent or capability needs no
  change to `mkdocs.yml`.
- The quickstart, concepts and results guides are authored in `docs/` too;
  they remain readable directly in the repository.
- The metric guide is `docs/field-guide.md`, a normal documentation page with
  the shared navigation, table of contents, theme and search.
- The documentation tab is titled "Nullius - Docs". Home, the header logo and
  the wordmark link to the landing page at `https://thinkflowlab.ai/nullius/`.
  Tabs use one transparent PNG favicon, with a versioned URL to refresh cached icons.
  The PNG and Apple touch icon are rendered from `assets/favicon.svg`: the mark
  alone, in the brand's white (`#e8e8e6`). Saved shortcuts
  can add their own platform background.
  Safari's pinned tabs use a separate black-on-transparent SVG mask.
- Fonts and their licences come from `app/static/fonts/`. No external font
  service is used. The README’s six animations use one fixed dark palette and live under
  `docs/assets/nullius/readme/`, generated by `python3 app/site/readme_media.py --write`
  (`--check` checks for drift). They are self-contained SVGs and respect reduced motion.

The figures are SVG files under `docs/diagrams/`, drawn by `app/site/diagrams.py`
(`--write` rewrites them, `--check` reports a stale one; the site test runs the
check). A page embeds a figure as an image, which GitHub renders as it is; the
build inlines it (`hooks.py`) so its colours follow the page's own variables in
both schemes. Nothing is loaded from outside the site.

The look is the documentation register of Harbor, e2e and boat: near-black or
light grey surfaces, DM Sans at 16px, a hairline rail with a bar on the current page,
bordered code panels with a language row, an on-this-page list with an active
bar, framed tables, one blue for where you are and where you can go. To try
another look, lay a stylesheet over the site's with `build.py --style <file>
--scheme default|slate --output dist/<name> --site-url http://localhost:8793/<name>/`;
the preview commits to one scheme, with no toggle.

`build.py` stages these inputs in a temporary directory, runs a strict build,
then removes the staging directory. `dist/` is the deployable artifact.
`check.py` checks the rendered links, assets, anchors and search targets. The
small tests run
with Python's standard library:

```bash
python3 -m unittest discover -s app/tests -p test_site.py
```

With the preview running and Playwright's Chromium installed, check navigation:

```bash
uv run --no-project --with playwright python app/site/check_navigation.py
```

This checks that lower sidebar links preserve the scroll position without a
full reload, and that the mobile drawer closes after navigation.

## Publishing

The host builds and publishes the site from `main` itself, through its
GitHub integration; nothing in this repository uploads anything. The site's
address is not in the repository: the host sets it as the `SITE_URL` build
variable, and the repository variable `DOCS_SITE_URL` holds the same value
for the check. The `documentation site` workflow is only that check, run by
hand from the Actions tab on any branch: it runs the same build and fails on
a broken link, asset, anchor or search target. Locally,
`bash app/site/host-build.sh` is the same check, for `http://localhost/`
unless `SITE_URL` is set.

`host-build.sh` is the build, for the host and the check alike: it installs
`requirements.txt`, builds for `SITE_URL`, checks, then lays the site out
under the URL's path in `deploy/` (beside `dist/`), with a redirect from the
root when there is a path. The site may be served at a path of a shared
domain that forwards the path to the host unchanged; the 404 page uses
absolute paths under the site URL, so the host serves the site under the
same path.

The host's project is set up once:

1. Connect it to this repository, production branch `main`.
2. Build command `bash app/site/host-build.sh`, output directory `deploy` under `app/site` (the script writes it),
   variables `PYTHON_VERSION` = `3.12` and `SITE_URL`, the full site root
   with a trailing slash; set the repository variable `DOCS_SITE_URL` to the
   same value so the check matches.
3. Gate the site's path on the domain and the host's own hostname behind an
   access policy with the allowed emails while the site is private.

Only the built site is served. Neither the application nor the repository's
internal files are published.

For another static host, serve that `deploy` directory the same way. Pass `--site-url` to
the build and checker for that host's URL; both root and subpath hosting work.

## Writing a page

The pages follow one shape, the one reference documentation sites use:

- The first line after the title is a one-sentence lead; it renders under
  the title. A paragraph is at most two sentences and only defines a concept.
- Anything enumerable is a table: fields, flags, files, rules, outcomes. The
  first column is the key, in code when it is a literal.
- Explain each option in one short description, without repeated openings
  such as "This chooses"; implementation details belong in the source.
- A procedure is a numbered list (rendered as steps); properties are bullets
  with a bold lead word.
- A callout is one or two lines: `!!! warning` for what stops a run or costs
  money, `!!! note` for a rule, `!!! tip` for a shortcut. A long list that is
  not needed first goes under `??? note "Title"`.
- Code blocks carry a title (` ```bash title="..." `); alternatives are tabs
  (`=== "Local"`).
- A page ends with a `grid cards` block of the next pages.
- No em dashes, no invented numbers, no proof dates or models.

The Supported sections, a README block and a page per entry, are generated from the catalogue by
`python3 app/tests/catalogue_docs.py --write`; `test_catalogue_docs.py` fails
when they are stale.
Benchmark citations use one expandable BibTeX panel. Long fields wrap for reading;
the copy button preserves the original citation text.

The static README header and three badges use outlined Instrument Serif and
DM Sans from the bundled fonts (and their existing licences). Refresh with
`uv run --no-project --with fonttools python app/site/readme_header.py --write`; use
`--check` to check for drift. One fixed palette works in both GitHub themes.
